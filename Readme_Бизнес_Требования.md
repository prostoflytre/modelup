## 1. Цель проекта

Создать дообученную языковую модель (LLM) на базе существующей модели, которая:

- улучшает качество ответов в учебном домене;
- персонализирует ответы под каждого ученика, взаимодействующего с моделью;
- помогает разобраться в теме конкретного занятия;

## 2. Область применения

Модель предназначена для помощи в учебных сценариях:

- объяснение тем заданных дисциплин по учебному плану;
- разбор ошибок, подсказки по шагам решения;
- персональное объяснение дидактических единиц темы;

### Не входит в область применения (Out of scope)

- медицинские/юридические советы с ответственностью за последствия;
- генерация вредоносных инструкций или запрещённого контента;
- выдача персональных данных или секретов.

## 3. Стейкхолдеры и роли

- **Заказчик/преподаватель**: определяет цели, принимает результаты.
- **Студент‑разработчик**: собирает данные, обучает, интегрирует в процесс.
- **Пользователь (студент)**: задаёт вопросы, получает персональные ответы/подсказки.

## 4. Критерии успеха (бизнес‑метрики)

Проект считается успешным, если:

- модель демонстрирует улучшение качества на подготовленном тест‑наборе по сравнению с базовой моделью;
- ответы в большинстве случаев (не менее 80% на ручной проверке) соответствуют требованиям к формату (см. раздел 6);
- процесс обучения воспроизводим (можно повторить обучение на тех же данных и получить сопоставимый результат);
- стоимость и время обучения укладываются в заданные ограничения (см. раздел 9).

## 5. Требования к данным

### 5.1. Источники данных

Допустимы:

- учебные материалы, методички, конспекты, задания и разборы;
- источники, объявленные в учебном плане;
- публичные источники, разрешённые для обучения.

Запрещены:

- тексты с персональными данными;
- закрытые материалы без разрешения;
- секреты/ключи/пароли.

### 5.2. Качество и подготовка данных

Минимальные требования:

- удаление дублей и мусорных строк;
- отсутствие PII/секретов;
- единый язык/стиль (или явная метка стиля, если используется несколько форматов);
- разделение на train/test.

## 6. Функциональные требования к модели

### 6.1. Входные данные

Модель принимает:

- текстовый запрос пользователя;
- метрики определённого занятия для конкретного обучающегося;
- тему занятия и свойственные ей дидактические единицы;
- информацию об обучающемся.

### 6.2. Выходные данные

Модель должна уметь:

- давать понятные объяснения с точки развития пользователя;
- доводить до решения запроса пользователя;
- давать короткий ответ, если запрос требует краткости;
- задавать уточняющие вопросы, если данных недостаточно;
- использовать информацию о пользователях из встроенных баз данных.

### 6.3. Ограничения поведения

- Если модель не уверена, она должна сообщать об этом и предлагать уточнить.
- Модель не должна придумывать факты в критичных задачах.

## 7. Нефункциональные требования

### 7.1. Производительность

- Целевое время ответа должно быть приемлемым для интерактивного использования в сети компьютеров.

### 7.2. Надёжность

- Процесс обучения должен завершаться без ручного вмешательства в типовых случаях.
- Автоматизация должна корректно обрабатывать ошибки инфраструктуры и продолжать использовать доступные ресурсы.

### 7.3. Безопасность и соответствие

- Не хранить и не публиковать приватные ключи/токены.
- Датасеты не должны содержать персональные данные.
- Модель не должна выдавать персональные данные других пользователей

## 8. Требования к процессу обучения (MLOps‑минимум)

### 8.1. Воспроизводимость

- Должны быть сохранены: версия кода, датасет (или ссылка/хэш), параметры обучения, артефакты.
- Артефакты обучения: веса адаптера LoRA, конфигурация, токенайзер.

### 8.2. Трассируемость

- Должно быть понятно, какая версия модели соответствует какому запуску обучения.
- Должны быть сохранены метрики/логи обучения (хотя бы базовые).

## 9. Ограничения и допущения

- Инфраструктура обучения арендуется в Vast.ai; стоимость зависит от выбранного GPU и времени обучения.
- Текущий пайплайн предполагает загрузку датасета на инстанс и запуск `python3 train.py`.
- В проекте применяется подход QLoRA для снижения требований к VRAM для использования более производительной модели.

## 10. Приёмка (Acceptance Criteria)

Результат принимается, если:

- существует обученный артефакт (папка с адаптером LoRA и токенайзером);
- на тест‑наборе/ручной проверке ответы улучшены относительно базовой модели;
- выполнены требования к формату ответа (понятность, шаги, отсутствие токсичности/утечек);
- модель персонализирует ответы под каждого ученика;
- модель корректно взаимодействует со всей предъявленной информацией.

## 11. Риски и меры

- **Галлюцинации** → тест‑набор, ручная проверка, требования «уточняй/не уверен».
- **Плохие данные** → чистка данных, запрет PII, удаление дублей.
- **Проблемы инфраструктуры (CDI/DNS/SSH)** → автоматический пропуск проблемных хостов/офферов, повторные попытки.
